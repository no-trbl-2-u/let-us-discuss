### [ ] [score 4.0] Quota visibility — surface remaining sessions/day before the user starts

- proposed: 2026-05-18, expand pass 1
- source signals:
  - Phase 9 ships per-account session quota (10/day, pinned
    in `config/limits.ts`) and graceful wrap UX at the cap —
    but the boardroom surface gives no proactive signal
    until the user has already burned a session.
  - Spec L33–37 makes "the persona feels the product before
    spending more time" load-bearing for v1; the same logic
    applies to spending session-quota.
  - Standard quota pattern across SaaS surfaces with daily
    caps.
- rationale: Anti-abuse limits exist (phase 9 shipped) but
  the user only learns about them by hitting them. A small
  "N/10 sessions left today, resets at midnight UTC" tile in
  the boardroom shelf (or on `/app`) lets the user spend
  remaining quota deliberately. Cheap, leverages existing
  data, no new schema.
- proposed scope: 1 phase — server-rendered count read from
  the same `quota.ts` helper phase 9 already uses; render in
  `components/boardroom/quota-tile.tsx` (or equivalent);
  unit test the count + reset boundary; no migrations.
- estimated phases: 1
- conflicts: none. Lives inside the boardroom surface;
  doesn't compete with phase 16's observability footer
  (token usage per session, not quota).
- best slot: post-phase 13, before phase 16 (so phase 16's
  observability footer can co-locate with quota if useful).
