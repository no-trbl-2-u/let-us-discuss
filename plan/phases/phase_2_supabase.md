# Phase 2 — Supabase wired

> Agent-facing brief. Concise, opinionated, decisive. Ship
> without asking; document any judgment calls in the commit
> body. Phase 1 stood up the substrate; this phase stands up
> Supabase's typed clients and proves connectivity with a
> guarded smoke route.

## Outcome

A typed Supabase client lives in `lib/supabase/`. A dev-only
`/_diag` route round-trips `select 1` against the configured
Postgres and renders the result. `.env.example` documents every
key already; `setup/03_supabase.md` is upgraded STUB → PARTIAL
(keys path captured, auth section still PARTIAL until phase 3).
Phases 3+ build on the server client without re-litigating
shape.

## Routes / endpoints (locked in `bearings.md`)

- `/api/health` — unchanged from phase 1 (no Supabase coupling).
- `/_diag` — **new, dev/preview only.** Server component reads
  `select 1` via the service-role client and renders
  `{ ok, value, env }`. Returns `notFound()` (HTTP 404) unless
  `DIAG_ENABLED=1` is present at runtime. Not part of the
  public URL contract; intentionally **not** listed in
  `bearings.md` URL contract. Phase 3+ may extend or remove.

## Content / data reads

| Helper | Lookup | Use |
|---|---|---|
| `createServerClient()` | `lib/supabase/server.ts` | Server components + server actions; per-request via `cookies()` (placeholder cookie store in phase 2; phase 3 wires the real one). |
| `createBrowserClient()` | `lib/supabase/client.ts` | Browser bundles (phase 3 is the first real consumer; phase 2 only ships the factory + a unit test that it returns a client). |
| `createServiceClient()` | `lib/supabase/server.ts` | Server-only, bypasses RLS. Used by `/_diag` and (later) admin scripts. |
| `runDiagProbe()` | `lib/supabase/diag.ts` | Pure helper consumed by the `/_diag` route. Returns `{ ok: true, value }` on success, `{ ok: false, reason }` on env-missing or query failure. |

No data fetched from the repo content layer; phase 4 introduces
`personas/`+`templates/` loaders.

## Components / handlers

This phase is mostly library code; no new visible components.
The `/_diag` page renders a small `<DiagPanel />` server
component inline — kept under `app/_diag/` because it has no
other consumers.

- `app/_diag/page.tsx` — server component. Calls
  `runDiagProbe()`; renders a typographic JSON-ish block.
- `lib/supabase/server.ts` — `createServerClient()`,
  `createServiceClient()`. Re-exports the `Database` type.
- `lib/supabase/client.ts` — `createBrowserClient()`. Reads
  `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
  These may be empty in phase 2; the factory throws only when
  actually called (phase 3 is the first call site).
- `lib/supabase/diag.ts` — `runDiagProbe()`. Reads env, picks
  service-role client, runs `select 1`. Pure error-handling;
  unit tested with a mocked client.
- `lib/supabase/database.types.ts` — placeholder `Database`
  type. Empty `public: { Tables: {} }`. Regenerated by
  `pnpm db:types` (script defined here, no-op until a migration
  exists).
- `db/migrations/.gitkeep` — empty directory; phase 3+
  populates.

## Empty / loading / error states

- **Disabled** (`DIAG_ENABLED !== '1'`): `notFound()`. Standard
  Next.js 404.
- **Missing env**: render the missing-env reason; HTTP 200.
- **Query error**: render `{ ok: false, reason: <message> }`;
  HTTP 200. (404 is reserved for "route disabled.")

No loading state — the page is fully server-rendered.

## Decisions made upfront — DO NOT ASK

- **SDK choice:** `@supabase/supabase-js` v2 + `@supabase/ssr`
  for the App Router cookie integration. (The legacy
  `@supabase/auth-helpers-nextjs` is deprecated; the ssr
  package is the v2 path.)
- **Cookies in phase 2:** `createServerClient()` accepts a
  cookies adapter, but phase 2 ships a placeholder
  `getServerCookieAdapter()` that returns the Next.js `cookies()`
  store. Phase 3 wires the real read/write set used by magic
  link. No auth happens in phase 2.
- **`Database` type:** placeholder; `pnpm db:types` is wired
  but exits 0 noting "no migrations yet." Regen happens phase
  3+ once tables exist.
- **`/_diag` gating:** `process.env.DIAG_ENABLED === '1'`.
  Default unset = 404 in prod. Set locally + on Vercel preview
  via env-var; do not set on production.
- **`/_diag` query:** `select 1` via `client.rpc()` is not
  possible without an existing RPC. Instead, use
  `client.from('non_existent').select('*').limit(0)` and
  catch — or better, `await client.auth.getSession()` since
  it round-trips the URL+anon-key without touching tables.
  **Choice:** `auth.getSession()`. The brief's "select 1" is
  a metaphor; the goal is to prove the SDK can reach the
  project. No tables exist yet, so a table-touching probe
  would always 4xx. (Phase 3+, after `auth.users` ships,
  the probe upgrades to a real table-touching query.)
- **`DATABASE_URL`:** not introduced in phase 2. SDK uses
  REST/PostgREST, not raw `psql`. `setup/03_supabase.md`
  notes that `DATABASE_URL` is captured for future use
  (migrations via `supabase` CLI) but not consumed by the
  Next.js runtime in v1.
- **Migrations tool:** `db/migrations/*.sql` directory exists
  but no tooling yet. Phase 3 ships the runner. For now,
  `pnpm db:migrate` exits 0 noting "no migrations yet."
- **Singleton vs per-request:** server clients are
  per-request (Next.js best practice for App Router); the
  module-level export is a *factory*, not an instance.
- **Test strategy:** unit tests cover the env-gating and
  diag-state shape. No live DB calls in tests. E2E does NOT
  hit `/_diag` (the route is disabled in the e2e build to
  keep the gate hermetic).

A brief that leaves Open Qs is a brief that fails its job.
